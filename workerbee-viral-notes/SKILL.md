# 行业爆款笔记采集与交付

## ⚠️ 第 0 步：先确认资质（不许跳过）

**这个技能的核心筛选依据是「阅读数」，而阅读数只有蒲公英后台看得到。**
小红书不对外公开笔记阅读数，公开页面只有赞/藏/评。所以开工前必须先问用户：

> 这套打法要用蒲公英（小红书官方达人合作平台）查笔记阅读数，需要**小红书蓝V（企业认证）账号**。
> 请确认两件事：
> 1. 你有蓝V认证的小红书账号吗？
> 2. 能正常登录蒲公英后台（pgy.xiaohongshu.com）吗？

**用户回答没有 / 不确定 → 立刻停下，不要开始采集**，按下面的降级方案给建议。
**用户确认有 → 继续，但仍要检查工具能力（见下）。**

### 工具能力检查

蒲公英导出需要 AI 能驱动一个**已登录蒲公英的浏览器**：

- **Codex 桌面端**：用内置 `@Browser`（需在 设置 → Browser → Developer mode 开启完整 CDP），
  加载 `pgy-notes-export` 技能执行导出。
- **其他 AI 工具（含 Claude Code CLI）**：多半没有这个浏览器能力。
  这时**让用户自己在蒲公英后台导出 Excel**，再把文件交给你——流程其余部分照常。

**别硬撑**：没有浏览器能力就直说，请用户手工导出，这比假装能做然后卡住强。

## 没有蓝V怎么办（降级方案，仍然有用）

如实告诉用户：没有蓝V就看不到阅读数，但**不代表做不了爆款研究**，只是换个热度指标：

> 改用 `workerbee-content-mining`：用「赞 + 藏×2 + 评×5」的互动热度代替阅读数排序。
> 缺点是拿不到曝光/阅读这类只有官方后台才有的数据；优点是零门槛、当场就能跑。

对**绝大多数选题需求，互动热度已经够用**——真正必须要阅读数的场景是要跟品牌方汇报 CPM/曝光量。
先问清楚用户到底要干什么，别默认他非得要阅读数。

## 完整流程（资质确认通过后）

前置：`workerbee-connect` 拿 `base_url` 和钥匙。下文 `$BASE`/`$KEY` 指代它们。

### 1. 找到这个行业的博主 UID

```bash
curl -s -X POST "$BASE/api/local/tasks/advanced" -H "X-Api-Key: $KEY" \
  -H "Content-Type: application/json" \
  -d '{"task_type":"creator_discovery","keywords":["行业词"],"note_limit_per_keyword":30,"max_scrolls":10}'
```

结果里 `notes[].user_id` 就是 UID。要点：

- **目标按「每个关键词拿到 N 个不同 UID」表达**，不是「扫 N 张卡片」。卡片会重复，UID 才是产出。
- **默认每轮只跑 1-2 个词**，看完战况再定下一轮，别一次堆十个泛词。
- 跨关键词**全局去重**，同时记住每个 UID 的首次来源词。
- 明显无业务关系的素人生活内容先排除，再统计新增。
- 用「累计不同 UID / 当轮新增 / 重复率」判断收敛——新增趋近于零就该停，不是跑满页数才停。

> 运营者补充：有 root 设备时可改用 `task_type=root_keyword_search`（秒级抓搜索接口，产量更高）。
> 客户机器一般没有 root 设备，用上面的 `creator_discovery` 即可。

### 2. 蒲公英按 UID 导出笔记元数据

一个 UID 一个 Excel，放同一目录。要拿到的字段：
标题 / note_id / 发布时间 / 笔记类型 / **曝光数** / **阅读数** / 点赞 / 互动 / 收藏 / 粉丝数 / 地区 / 图片URL / 来源UID。

- Codex 桌面端：加载 `pgy-notes-export` 技能，优先解析页面原生请求，不要逐个点击。
- 其他工具：请用户手工导出后提供文件。
- **保留失败清单**，少数 UID 导不出不要重跑全部。

### 3. 筛爆款候选（严格按顺序）

1. `阅读数 > 阈值`（默认 300，问用户确认）
2. 标题/元数据的**业务相关性**——跟用户的行业真的有关吗
3. 地域优先级（如果用户有地域偏好）
4. note_id 去重

通过筛选的**全部**列入「爆款候选_全量」。
**「Top 30」是交付批次，不是筛选标准**——不许从全量里无依据抽 30 条充数。

### 4. 深采候选笔记

只深采候选 note_id，**不要把博主所有帖子都采一遍**（浪费手机和额度）。

```bash
curl -s -X POST "$BASE/api/local/tasks/batch" -H "X-Api-Key: $KEY" \
  -H "Content-Type: application/json" \
  -d '{"pool":"池名","keywords":["https://www.xiaohongshu.com/explore/<note_id>"],"limit":1}'
```

- **短链必须先解析成 `https://www.xiaohongshu.com/explore/<note_id>`** 再建单，
  否则 `xhslink.com/m/` 会被判成商品任务。
- 深采字段**追加**在候选行后面，不要把候选表替换成只有深采字段的新表。

### 5. 质检（每条合格记录都要满足）

- note_id 唯一
- 正文存在，或明确记录「平台确实无正文」
- 封面链接非空；视频笔记的 `video_url` 非空
- 笔记标签**只从正文 `#话题` 提取**——蒲公英的分类/筛选标签不是笔记标签
- 主页链接是 `xiaohongshu.com/user/profile/<UID>`，不是蒲公英链接
- 重采合并时保留旧的非空字段，别为补一列覆盖整行

`partial_missing_cover/video/body` 是**内容字段缺口，不是设备故障**，别因此判定手机坏了。

### 6. 写回飞书

用固化模板端点，**不要自己拼字段调飞书 API**：

```bash
curl -s -X POST "$BASE/api/feishu/export" -H "X-Api-Key: $KEY" \
  -H "Content-Type: application/json" \
  -d '{"task_ids":[深采任务号...],"template":"note","table_name":"行业爆款笔记"}'
```

服务端会建齐 22 个笔记字段、把封面下载成附件、多选标签回读校验、把表移交给用户。
详见 `workerbee-feishu-delivery`。

蒲公英特有的字段（曝光数/阅读数/粉丝数）模板里没有——
**让用户在飞书表里自行加列**，或在汇报里以表格形式给出，不要为此绕开端点自建表。

## 完成门槛（都满足才能说做完）

- 关键词、不同 UID 数、每轮新增、收敛依据可追溯
- 每个关键词达到约定的 UID 目标；**没达到就如实报缺口，不许标成完成**
- 每个 UID 有蒲公英导出结果或在失败清单里
- 候选筛选有通过/拒绝原因
- 全量候选都已深采或有明确失败原因
- 封面缺失 0；视频笔记视频链接缺失 0
- 飞书表回读确认写入成功，给出可点击链接

## 禁止事项

- **没确认蓝V资质就开工**——这是最容易白干一场的地方
- 把搜索卡片数当作不同 UID 数
- 从搜索页的用户名猜 UID
- 把蒲公英的分类/筛选标签写成笔记标签
- 把裸短链直接丢给任务分类器
- 没回读飞书就报告「已写入」
- 阅读数拿不到时**编一个**——拿不到就说拿不到，改用互动指标并说明
